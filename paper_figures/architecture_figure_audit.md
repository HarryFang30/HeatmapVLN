# Architecture Figure Audit

## Scope and evidence standard

This document audits the semantics of the two canonical CVPR main-paper figures:

- **Figure A:** `fig_method_overview.*`
- **Figure B:** `fig_heatmap_module.*`

This is a **static source/configuration audit, not a runtime-hook audit**. It verifies declared data flow, tensor contracts, parameter freezing, and module placement from the source snapshot available on 2026-08-12. It does **not** prove that a particular evaluation process loaded the intended checkpoints, exercised every depicted branch, or produced the declared tensors at runtime. Line numbers refer to the authoritative server checkout at `/mnt/afs/lixiaoou/intern/fjl/HeatmapVLN` and may drift after later edits.

Confidence labels:

- **High:** directly established by executable source and the formal control-training configuration.
- **Medium:** the source supports the interpretation, but the figure intentionally abstracts runtime state, scheduling, or process boundaries.
- **Unresolved:** static code cannot establish the relevant checkpoint or evaluated-run provenance.

## Training-state audit

The formal heatmap-control configuration trains exactly the shared structured tokenizer and the 12 per-block heatmap-control adapters. It freezes Qwen2.5-VL, Qwen.visual, the Heatmap Head, native latent bridge, visual memory, all native NextDiT parameters, and the action encoder/decoder. The control objective is trajectory flow-matching MSE; there is no heatmap loss in this stage. Evidence: `configs/heatmap_system1_control_8gpu.yaml:183-247`, `scripts/training/model_builder.py:394-440,443-539`, and `src/models/action/nextdit_action_head.py:659-706`.

Optimizer groups in the audited configuration are AdamW with tokenizer LR `1e-4`, ordinary adapter LR `5e-5`, gate LR `1e-4`, weight decay `0.01` for ordinary weights, and no decay for norm/bias/gate tensors. The tokenizer and adapters are explicitly kept in FP32 even though the surrounding training autocast policy is BF16. Evidence: `configs/heatmap_system1_control_8gpu.yaml:226-240` and `scripts/training/optimizer.py:15-48,271-342,436-492`.

## AMB3R pose-adaptation checkpoint ambiguity

The repository contains a concrete AMB3R pose-cache contract, a pose-adaptation configuration/launcher, and a whitelist for adapting pose-sensitive Heatmap Head modules. Static source therefore supports the **intended** AMB3R-conditioned method shown in the figures. It does not establish the following artifact facts:

1. whether a completed, validated AMB3R pose-adaptation checkpoint currently exists;
2. whether the heatmap checkpoint supplied to the control-training launcher was the original GT-pose-trained checkpoint or an AMB3R-adapted successor;
3. whether the reported closed-loop evaluation loaded that exact adapted checkpoint and selected `amb3r_vo_da3` as its runtime pose provider.

The local paper-figure README states that the prepared AMB3R pose-domain adaptation stage had not yet produced a trained checkpoint when it was written. The server may have changed since that statement. Consequently, the figure should be described as the **method/intended deployment architecture** until a runtime provenance record identifies the Heatmap Head checkpoint, AMB3R model checkpoint, pose provider, and evaluated control checkpoint. A camera-ready empirical claim such as “our reported navigation result uses the AMB3R-adapted head” requires that additional artifact-level verification.
