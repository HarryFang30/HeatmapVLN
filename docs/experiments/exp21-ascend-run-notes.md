# EXP-21 敏感性点搬到昇腾 910B：运行记录

判据和设置在 [`README.md` 的 EXP-21 节](README.md#exp-21-参数敏感性历史帧数-k快系统采样条数-s去噪步数-m)。
这份只记**这一轮在昇腾上实际怎么跑的、为什么那样跑、以及哪些地方偏离了预注册**。

## 这一轮的性质：用户明确放宽了门槛

EXP-21 的预注册写的是「种子 42；4090。默认点在 4090 上，所以敏感性点也必须在 4090 上跑。
如果改到华为机器上，要先在那边对同 500 集重跑默认点」，而 EXP-22 的判据又是总门
（H1 不过，910B 上一个数都不能报）。

**2026-10-10，用户明确指示**：敏感性测试直接在昇腾上跑，不必按预注册的严格顺序，EXP-22 的
H1 不作为前置。所以：

- **EXP-22 H1 没有过**（P1 判「没测出来」，见 `../ops/ascend_910b_open_problems.md` §0.6）。
  这一轮的数**不是** EXP-22 认证过的平台上产出的。
- 仍然成立的是 EXP-21 自己的核心要求：**同平台、同种子、同 500 集的配对比较**。默认点也在
  昇腾上跑，所有点与它配对，所以**点与点之间的差值是内部一致的**。
- **不成立的是跨平台**：这些绝对数不能和 4090 的放在同一张表，也不能和 4090 上已经在跑的
  两个点（`exp21_m2_seed42_4090`、`exp21_s1_seed42_4090`）混在一张图里。混了就是把两个
  平台的噪声当成参数效应。
- 同机两遍逐调用一致**没有验证过**，所以这一轮的任何单点差值都无法区分「参数效应」和
  「这台机器的运行间抖动」。要区分就得补 H1。

写清楚这些不是为了给结论打折，是为了让看图的人知道这张图能支撑到哪一步。

## 跑之前必须先修掉的东西

搬过来第一次尝试（EXP-22 P1）死在第二集。根因在
[`../ops/ascend_910b_open_problems.md` §0.6](../ops/ascend_910b_open_problems.md)：
**CANN 的图引擎要不到自己的约 800 MiB 设备内存**，因为 PyTorch 的缓存分配器把整张卡拿走了
（一集之后空载仍 65521 / 65536 MiB，而活张量只有约 40 GB）。AI CPU 报 oom 后无限重试，
表现为卡住，九分钟后以 507017 收场。

`81dfa08` 的两条处置（都不改变数值）：

| 改动 | 效果（实测） |
|---|---|
| 启动脚本设 `PYTORCH_NPU_ALLOC_CONF=expandable_segments:True` | 负载下整卡从 65521 MiB 降到约 48000 MiB |
| 里程计后端在 `reset()` 里 `empty_cache()` | 新一集开始时再掉到约 40200 MiB |

即从 **15 MiB 余量** 变成 **约 25 GB 余量**。验证：同样那 4 集金丝雀，之前两次都死在
`zsNo4HB9uLZ/25` 的第 20 帧建图初始化，这次跑到第 45 帧、`revision=9`，地图已建好。

## 布局：为什么是 6 槽而不是 8

| 项 | 值 | 为什么 |
|---|---|---|
| 910B 槽位 | **6**（卡 0–5），一卡一槽（模型 + 里程计同卡） | 客户端启动脚本要求每槽一个**不重复**的 GPU id，而 4090 只有 6 张卡。起 8 个服务端也只能驱动 6 个 |
| 卡 6、7 | 空着 | 留给第二套带 S 或 M 覆盖的服务端（那两组是服务端侧开关，必须另起） |
| 分片 | 8（`subset500` 的 8 片，共 500 集） | 预注册的子集 |
| 分片顺序 | `3,4,2,0,7,6,1,5` | 启动脚本按 `slot = idx % 槽数` 分配，所以拿两片的是槽 0 和 1。各片集数是 71 54 65 49 56 59 74 72，这个顺序让它们拿到 103 和 115 集，而不是默认顺序的 145 |
| 重试 | 客户端 `PPA_EVAL_SHARD_RETRIES=3`，驱动脚本每个点最多 3 次 | 无人值守 |

**驱动脚本**：`/workspace/exp21ascend/driver.sh`（容器内，`nohup setsid`），日志
`/workspace/exp21ascend/driver.log`。它只跑**不需要服务端覆盖**的点，所以一套服务端服务全部
四个点，脚本**完全不需要碰 910B**（容器里只有受限的隧道密钥，开不了 shell，这是故意的）。

点的顺序：**默认点 → K=5 → K=7 → K=6**。默认点第一，因为所有差值都与它配对；之后极值
先于中间值，这样中途被打断也能保住曲线两端。

一个槽死掉时：驱动脚本会探活 52400–52405，按**活着的前缀**降级重跑（客户端允许服务端声明
的槽位数多于本次使用的，但端口必须是前 N 个，所以中间断一个就只能用它前面的）。它**不能**
重启服务端。

## 还没跑的

- **S ∈ {1, 8, 64} 和 M ∈ {2, 5, 20} 六个点**：都是服务端侧覆盖
  （`PPA_EVAL_NUM_SAMPLE_TRAJS` / `PPA_EVAL_NUM_INFERENCE_STEPS`），每个点要另起一套服务端。
  可以用空着的卡 6、7 并发跑，但端口基址受隧道密钥的 `permitopen` 限制（只开了 52400–52407
  和 52500–52507），所以要么改授权，要么等前一组跑完腾出端口。
- **子集代表性检查**：预注册要求「默认点在子集上的 SR 与全量 SR 之差在 ±3pt 内」。昇腾上
  没有全量 A0，所以这一条在昇腾上**暂时无法判**；4090 的全量 A0 是 62.70%，可以作描述性
  参照，但那是跨平台的，不能当判据。
- **配对 bootstrap（2000 次）**：跑完点之后做，脚本按预注册用同 500 集配对。
